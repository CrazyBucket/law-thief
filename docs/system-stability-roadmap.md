# 系统稳定性治理方案

## 文档目的

本文档用于给当前项目的系统稳定性治理排优先级，统一团队对问题现状、治理目标、执行顺序和注意事项的理解。

它不替代具体模块说明文档。像事件批处理、动画消费规则这类局部机制，仍应由专项文档维护；本文档关注的是更上层的系统治理与落地顺序。

## 背景现状

当前项目已经从功能原型阶段进入机制组合快速增长阶段，主要特征如下：

- 战斗规则链路变长：一次攻击会串联命中、护甲、位移、状态、宝石效果、死亡钩子、AI 意图刷新等多个阶段。
- 表现链路复杂：真实 `GameState`、展示快照、事件流三套时序并存，任何一处不同步都会表现为动画错乱、特效异常或状态跳变。
- 位移规则分散：正常移动、拉拽、击退、碰撞、落点、链式推动等逻辑没有完全收口到统一模型。
- AI 预览与执行存在漂移风险：意图预计算依赖当前世界状态，但执行过程中会被前序事件持续改写。
- 测试已有基础，但仍以专项 case 为主，系统级不变量和随机压力验证不足。

这些问题叠加后，会形成一种典型体验：功能不是完全不可用，但试玩一段时间后，攻击特效、寻路、碰撞、动画等环节会持续冒出问题，且问题之间存在连锁关系。

## 总目标

本轮治理的目标不是“把所有 bug 一次修完”，而是分三层建立稳定性能力：

- 止血：先阻止系统继续快速长出新的结构性问题。
- 收口：把高风险规则统一到更清晰的边界和入口上。
- 提效：为后续新增机制提供更稳定的接入方式，降低每次改动的回归成本。

换句话说，本方案追求的是“让系统逐步变得可控”，而不是短期追求表面上的问题清零。

## 治理原则

### 1. 先让问题更早暴露，再谈更优雅的重构

如果错误只能靠手玩发现，那么系统复杂度只会持续压垮开发效率。优先建设校验、断言和回归门槛，让错误在测试或调试阶段尽早失败。

### 2. 规则层只保留一份业务真相

业务结算应尽量在规则层完成，表现层负责消费结果，不再额外推断业务状态。这样可以降低动画、特效和真实状态之间的漂移。

### 3. 所有位置变化尽量走统一入口

只要一个机制会改变单位位置，就应该纳入统一的位移、碰撞、落点和占格语义，而不是在不同模块内各自维护一套“差不多”的逻辑。

### 4. 用不变量保护系统，而不是只靠功能 case

专项 case 负责覆盖具体玩法，不变量负责兜底系统不会进入非法状态。两者都需要，且不变量优先级更高。

## 优先级方案

## P0：止血层

### 目标

优先建立“出错能被及时发现”的能力，降低靠手工试玩兜底的比例。

### 具体方向

- 建立系统级不变量校验：
  - 死亡单位不得继续占格。
  - 一个格子不能同时被多个单位占用。
  - 占格索引与单位真实 occupied cells 保持一致。
  - 所有单位位置必须在边界内。
  - 多格单位 footprint 不允许部分越界或非法重叠。
- 为事件流增加基础校验：
  - 检查关键事件是否缺失必要字段。
  - 检查当前动画批处理依赖的顺序约束是否被破坏。
  - 在调试模式下尽早暴露非法事件。
- 固化最低回归门槛：
  - 任何涉及 `scripts/battle/`、`scripts/rules/`、`scripts/ui/` 的改动，都必须重新执行既有战斗回归。
  - 对已经出现过回归的链路，优先补成自动化 case。
- 增加随机压力测试：
  - 用固定 seed 复现问题。
  - 随机执行多回合动作序列。
  - 每一步后校验不变量并打印关键上下文。

### 完成标志

- 明显非法状态可以在测试或调试中尽早暴露。
- 每次改动后至少有一组固定回归能兜住主链路。
- “只能手玩才能发现”的问题比例明显下降。

### 注意事项

- 这一阶段先不要做大规模架构重写。
- 重点不是消灭所有 bug，而是建立止损机制。
- 校验优先放在测试和调试路径，避免影响正常体验节奏。

## P1：统一位移、碰撞与占格语义

### 目标

把最容易导致寻路、碰撞、强制位移异常的逻辑收拢到统一模型中。

### 具体方向

- 统一位置变化入口：
  - 正常移动
  - 拉拽
  - 击退
  - 冲刺
  - 链式推动
- 统一碰撞结算语义：
  - 撞墙何时发生
  - 撞单位何时发生
  - 碰撞伤害如何分配
  - 被阻挡后的落点如何确定
  - 是否触发 `forced_move`、`on_contact`、tile enter 等后续逻辑
- 清理局部近似实现：
  - 逐步减少各模块自行维护的贪心位移逻辑。
  - 把通行、落点、碰撞、边界校验尽量收敛到统一工具层。
- 优先补多格单位 case：
  - footprint passable
  - 占格同步
  - 贴边移动
  - 推拉后的 anchor 合法性

### 完成标志

- 玩家移动、AI 移动、拉拽、击退等行为遵循同类规则。
- 多格单位在边界、障碍物附近的行为更加稳定。
- 碰撞与落点逻辑可以被清晰描述，而不再依赖来源特判。

### 注意事项

- 不要以“修当前 case”为目标到处补特判。
- 应先统一语义，再逐步迁移各来源逻辑。
- 迁移中必须保留旧回归，并补针对新入口的测试。

## P2：收敛事件流与表现层边界

### 目标

降低规则层、事件流和表现层之间的状态漂移风险，让动画问题更容易定位。

### 具体方向

- 将关键事件从“动画提示”逐步升级为“状态变化记录”：
  - `damage` 不只包含位置和伤害值，还应逐步补齐目标标识和关键结果。
  - `move_step` 应明确来源位置、目标位置和主体标识。
- 为关键事件建立稳定 schema：
  - 哪些字段必填。
  - 哪些字段可选。
  - 哪些事件必须成组或连续出现。
- 减少表现层业务推理：
  - UI 以消费规则层结果为主。
  - 避免通过“当前位置猜测谁受伤、谁死亡、谁被位移”。
- 把当前批处理约束从文档约定逐步升级为可校验规则。

### 完成标志

- 事件流结构更清晰，问题更容易定位到规则层还是表现层。
- 动画顺序错误能更快复盘，不再大量依赖肉眼猜测。
- 表现层不再承担过多业务真相恢复工作。

### 注意事项

- 不要一次性重写整套事件系统。
- 先从高频、易错事件类型切入，例如：`move_step`、`damage`、`explode`、`projectile`。
- 任何事件字段调整，都要同步检查消费逻辑与回归脚本。

## P3：压缩 AI 预览与执行漂移

### 目标

提高敌方意图预览的可信度，减少“预览看起来合理，执行结果却偏掉”的体验问题。

### 具体方向

- 明确预览的承诺边界：
  - 哪些效果必须准确预览。
  - 哪些连锁效果允许近似提示。
  - 哪些随机结果应在表现上明确告知不确定性。
- 对关键敌人行为建立一致性回归：
  - 路径
  - 目标
  - 影响范围
  - 关键副作用
- 减少意图系统对短时动态副作用的脆弱依赖。
- 针对高随机性行为单独标识，避免玩家把随机差异误判为系统错误。

### 完成标志

- 常规情况下，敌方意图预览与执行结果高度一致。
- 偏差主要来自已知随机性，而不是系统漂移。
- 玩家更容易理解敌人的行动逻辑。

### 注意事项

- 不要强求所有复杂连锁 100% 预览一致。
- 重点是避免核心行为层面的“打脸”，而不是追求过度精确的视觉承诺。

## P4：形成长期扩展规范

### 目标

在系统边界收稳后，为后续新增 gem、怪物、状态、地块效果降低接入风险。

### 具体方向

- 建立机制接入 checklist：
  - 是否影响攻击流程
  - 是否影响位移/碰撞
  - 是否影响意图预览
  - 是否产出事件
  - 是否需要专项测试
  - 是否需要新增批处理规则
- 补齐系统总览文档：
  - 哪些模块负责业务真相
  - 哪些模块只做表现
  - 状态变化从哪里进入
  - 回归应该覆盖哪些关键链路
- 逐步减少散落特判，把新增逻辑收口到统一扩展点。

### 完成标志

- 新增机制时可以按 checklist 接入，而不是完全依赖经验。
- 系统知识不只存在于代码上下文或个人记忆里。
- 回归范围和风险点更容易被提前评估。

### 注意事项

- 这一阶段排在前面几个阶段之后。
- 如果止血和收口还没完成，不要过早投入过多时间在“写规范”上。

## 推荐推进顺序

建议按以下顺序执行：

1. 先做 P0，建立止血能力。
2. 再做 P1，统一位移、碰撞和占格语义。
3. 然后做 P2，收紧事件流与表现层边界。
4. 再做 P3，压 AI 预览与执行漂移。
5. 最后做 P4，沉淀长期扩展规范。

如果人力有限，建议始终遵循一个原则：

- 宁可先把错误更早暴露出来，也不要继续把复杂度埋进特判里。

## 与现有文档的关系

- `docs/event-animation-guide.md`：聚焦事件动画系统的消费顺序、批处理方法和常见陷阱。
- 本文档：聚焦整体系统稳定性治理的优先级、目标和推进顺序。

两者是上下层关系：动画文档回答“事件如何正确播放”，本文档回答“为什么当前系统容易出问题，以及应该先治理哪一层”。

## 当前阶段建议

如果只选择一件事先做，建议优先从 P0 开始，并把最小交付定义为：

- 补一组系统级不变量检查。
- 固化战斗主链路回归命令。
- 增加一个随机压力测试入口。

这是当前性价比最高、且最能直接改善试玩体验的一步。
