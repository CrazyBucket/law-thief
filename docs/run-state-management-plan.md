# 游戏状态管理方案

## 文档目标

本文档用于统一一整局游戏的状态边界、持久化职责和跨场景继承规则，保证从“开始新局”到“完成整局 / 失败退出”的主流程能够串通，并让战斗之间的玩家状态继承稳定、可恢复、可继续扩展。

它重点回答四个问题：

- 一局游戏到底有哪些状态，分别归谁管。
- 玩家在一场战斗里变化了什么，哪些要带到下一场。
- 地图节点进入、结算、返回时，如何避免重复发奖励或重复回血。
- 休息点、问号、商店、宝石携带这些局内系统，如何落到统一的 run state 上。

## 设计范围

本方案覆盖以下链路：

- 选择存档位并开始新局。
- 生成地图并进入节点。
- 进入普通战 / 精英战。
- 战斗胜利后返回地图。
- 休息点、问号、商店、终点这类非战斗节点结算。
- 宝石、遗物、玩家生命值在多场战斗之间的继承。
- 战斗失败时整局结束。

当前不展开的部分：

- 商店经济与商品购买。
- 章节切换 / Boss 结算。
- 局外成长与 meta progression。
- 地图外的完整背包 UI。

## 状态分层

### 1. Session State

只负责当前界面跳转时的临时上下文，不承担整局真相。

当前由 `GameService` 承担，主要字段：

- `pending_encounter_id`：即将进入的遭遇战。
- `pending_room_id`：当前地图节点 id。
- `adventure_return`：本场战斗结束后是否回到冒险地图。

这一层只解决“从哪个场景跳到哪个场景”，不保存玩家持久数据。

### 2. Run State

`RunState` 是整局唯一的持久业务真相，负责保存“这局游戏已经走到了哪、玩家目前带着什么”。

当前已纳入 `RunState` 的核心内容：

- 种子：`master_seed`、`map_seed`
- 遗物：`owned_relics`、`relic_runtime`
- 遗物奖励快照：`relic_offer_snapshots`
- 持久槽位变化：`extra_slots`、`upgraded_slots`
- 玩家跨战斗生命：`player_hp`、`player_max_hp`
- 玩家当前槽位宝石快照：`player_slot_gems`
- 玩家手持宝石快照：`carried_gem`
- 非战斗房间结算快照：`resolved_rooms`

原则上，只要一个状态要跨场战继承，就应该优先进入 `RunState`，而不是只留在某个场景节点里。

### 3. Adventure Progress State

`AdventureService` 负责地图进度与当前房间上下文，主要保存：

- 当前地图矩阵
- 当前所在坐标
- 当前待进入房间类型与标签

它通过 `RunService.set_progress_payload()` 存进 run save，但它本身不负责保存玩家战斗成长数据。

### 4. Battle State

`GameState` 只表示“当前这一场战斗”的即时状态，包括：

- 单位、地块、实体
- 当前回合、行动阶段
- 当前场上的宝石
- 当前手持宝石 `held_gem_uid`

战斗中的所有规则都基于 `GameState` 结算；但战斗结束时，需要把应继承的数据回写到 `RunState`。

## 全流程主链路

### 1. 开始新局

入口：`AdventureService.start_new_run()`

流程：

1. 确定本局种子。
2. `RunService.start_run()` 创建新的 `RunState`。
3. 生成冒险地图。
4. 初始化当前位置为起点。
5. 保存地图进度到 `progress_payload`。

这一步建立的是“整局容器”，不是单场战斗容器。

### 2. 点击地图节点

入口：`AdventureService.enter_cell()`

流程：

1. 更新 `current_pos`。
2. 记录 `pending_room_type` / `pending_room_label`。
3. 先同步地图进度。
4. 根据房间类型跳转：
   - 战斗节点 -> 进入 `battle_scene`
   - 非战斗节点 -> 进入 `room_placeholder`

同时，`current_room_id()` 统一把节点坐标转换为 `x_y`，作为房间结算与奖励快照的主键。

### 3. 进入战斗

入口：`BattleScene -> BattleController.start_encounter() -> DataRegistry.create_battle_state()`

创建战斗状态时，玩家部分不再只从 `unit_player` 默认模板生成，而是按以下顺序恢复：

1. 先创建基础玩家单位。
2. 应用 `RunState` 中的持久槽位变化。
3. 恢复玩家生命值。
4. 恢复每个槽位上的宝石。
5. 恢复玩家当前手持宝石。

这样下一场战斗看到的玩家，就是上一场战斗结束后留下来的玩家，而不是一个被重新初始化的模板角色。

### 4. 战斗中状态变化

战斗里会发生两类变化：

- 只在本战有效：回合标记、临时状态、AI 意图、事件流。
- 要跨战继承：玩家 hp、max_hp、玩家槽位中的宝石、手持宝石。

当前策略是：

- 战斗进行中仍以 `GameState` 为准。
- 在关键保存时机，把玩家跨战数据抽取回 `RunState`。

### 5. 战斗胜利后返回地图

胜利结算时：

1. 先记录图鉴 / 历史结果。
2. 把当前玩家战斗状态回写到 `RunState`。
3. 如有战后遗物奖励，先走奖励选择。
4. 再返回地图。

这样可以保证：

- 当前生命值会正确继承到下一场。
- 当前槽位上的宝石会带到下一场。
- 手里拔出来但没插回去的宝石，也会带到下一场。

### 6. 战斗失败

失败即整局结束：

1. `RunService.end_run()` 清掉当前 run save。
2. 清空本地 adventure 状态。
3. 返回主界面。

这样可以避免失败后继续使用一份残留 run state。

## 非战斗房间结算规则

### 1. 休息点

规则：恢复玩家最大生命值的 20%。

当前实现：

- 结算入口统一收口到 `AdventureService.resolve_pending_room()`。
- 恢复逻辑写入 `RunService.heal_player_percent(0.2)`。
- 回血结果直接写回 `RunState.player_hp`。
- 房间结算结果写入 `resolved_rooms[room_id]`，避免重进后重复回血。

### 2. 问号节点

规则：不再走随机事件文本分支，当前统一改为“直接获得 1 个遗物”。

当前实现：

- 仍保留房间类型 `EVENT`，但语义上视为“遗物节点”。
- 进入房间时通过 `RunService.get_or_roll_relic_offer(room_id, "normal_chest", 1)` 生成一个候选。
- 直接发放给玩家，并记录到 `resolved_rooms`，避免重复领取。
- 地图显示从问号改为遗物图标。

### 3. 商店

规则：先保留节点，不接入交易逻辑。

当前状态：

- 地图仍然会生成商店节点。
- 进入后只展示占位说明。
- 不做任何资源或状态结算。

这样做的目的是先把状态主链路串通，再接经济系统，而不是把“有没有商店”与“状态能不能继承”耦在一起。

## 宝石跨战携带方案

### 目标

玩家宝石不再只属于单场战斗，而是属于整局 run 的一部分。

### 当前落地规则

#### 1. 槽位中的宝石会继承

战斗胜利后，玩家各槽位上的宝石会被序列化到 `RunState.player_slot_gems`。

进入下一场战斗时，再从快照恢复回玩家槽位。

#### 2. 手持中的宝石也会继承

如果玩家在一场战斗结束时，手里还拿着一颗宝石，没有插回去：

- 这颗宝石会保存到 `RunState.carried_gem`
- 下一场战斗开始时，会继续以手持状态恢复

这就满足了“宝石可以带在身上”的需求。

#### 3. 继承范围只包含玩家侧

当前方案只持久化玩家侧的：

- 玩家 hp / max_hp
- 玩家槽位中的宝石
- 玩家手持宝石

敌人、场地、地块槽位上的宝石仍属于单场战斗局部状态，不跨战保存。

### 为什么这样设计

因为整局成长的主体是玩家，而不是某一张具体战斗棋盘。

如果把敌人身上的宝石、地块上的宝石也一起持久化，会把“房间状态持久化”和“玩家 build 持久化”混在一起，后续会让地图回溯、逃跑、房间重打等语义变得很乱。

所以当前先明确：

- 玩家 build 跨战继承。
- 房间内局部对象默认不跨战继承。

## 防重复结算策略

### 房间结果快照

`resolved_rooms` 用来记录某个房间是否已经结算过。

适用场景：

- 休息点已经回血，重新进入不能再回。
- 问号节点已经发遗物，重新进入不能再发。

这层的目标不是做复杂回滚，而是保证“同一个节点不会因为 reload / continue 被重复结算”。

### 遗物候选快照

`relic_offer_snapshots` 保证同一个房间重进时，奖励候选不会漂移。

这和 `resolved_rooms` 分工不同：

- `relic_offer_snapshots` 解决“候选一致”。
- `resolved_rooms` 解决“结果只生效一次”。

两者叠加后，房间奖励才是稳定的。

## 现在的职责划分

### `RunService`

负责：

- run 的创建、保存、加载、结束
- 遗物持有与奖励候选快照
- 玩家跨战状态的捕获与恢复源数据
- 非战斗房间的持久化结果记录

### `AdventureService`

负责：

- 地图推进
- 当前房间上下文
- 非战斗房间入口与统一结算调度

### `DataRegistry`

负责：

- 创建新的 `GameState`
- 根据 `RunState` 恢复玩家槽位、生命与宝石状态

### `BattleScene / BattleController`

负责：

- 战斗内结算
- 胜利后把可继承状态回写到 `RunState`
- 失败后结束整局

## 当前已落地内容

本轮已经落地的行为包括：

- 新增 run 级玩家生命值持久化。
- 新增 run 级玩家槽位宝石持久化。
- 新增 run 级手持宝石持久化。
- 休息点固定回血 20%。
- 问号节点改为直接获得一个遗物。
- 商店节点保留占位，不做结算。
- 房间结果增加去重结算保护。
- 战斗失败时结束整局并清理 run。

## 后续建议

建议按下面顺序继续往下做：

1. 给冒险地图 HUD 增加玩家当前 hp / relic / gem 摘要，方便看跨战状态是否正确。
2. 给商店接入真正的商品池，并区分遗物 / 宝石 / 消耗品。
3. 给地图外增加简单的 run inventory 视图，能在非战斗节点查看当前 build。
4. 给房间结算补自动化回归，覆盖：休息点、问号、战斗胜利继承、战斗失败清档。
5. 后续如果要支持“房间可回访”或“跳过后再进”，再进一步细化 `resolved_rooms` 的状态结构。

## 验收口径

当下面几件事都成立时，可以认为这套主链路已经基本串通：

- 新开一局后，可以连续打多场战斗，生命值会正确延续。
- 上一场战斗结束时玩家槽位上的宝石，下一场还能看到。
- 手里拿着的宝石不插回去，下一场仍然在手里。
- 同一个休息点不会重复回血。
- 同一个问号节点不会重复发遗物。
- 战斗失败后，继续游戏不会回到一份已经失效的 run。

这就是当前阶段“全流程串通”的最小可用标准。
