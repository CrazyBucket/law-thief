# UI/UX Optimization TODO

## Purpose

当前项目的战斗规则和系统验证已经有基础，但玩家可见 UI 还停留在工具化/原型化阶段。下一轮 UI 改造目标不是单纯“做漂亮”，而是让游戏信息更可信、更有层级、更像一个成熟战棋/肉鸽游戏，而不是像调试面板或网页按钮集合。

这篇文档聚焦四个高收益方向：

1. 地图选关卡 UI
2. 战斗场上高亮、范围、路线、意图的统一渲染
3. 下方行动操作区的游戏化重构
4. 玩家可见文案与代码注释规则

相关代码入口：

```text
scripts/ui/adventure_map_scene.gd
scripts/map/tile_renderer.gd
scripts/map/adventure_room_display.gd
scripts/ui/isometric_board.gd
scripts/ui/battle_scene.gd
scripts/ui/battle_hud_presenter.gd
scripts/ui/battle_ui_theme.gd
scripts/ui/ui_palette.gd
scripts/ui/slot_popup.gd
localization/strings.csv
```

## Current Problems

### 1. 地图选关卡 UI 太像临时调试页

当前地图页主要是棋盘格 + 顶部文本 + hover 预览。它能用，但缺少“路线选择”的游戏感：

- 当前房间、可选房间、已结算房间的视觉层级不够明确。
- 房间节点没有形成足够强的路线、章节、风险、奖励感。
- 预览面板仍在展示坐标、层数、事件 id、规则 id 等偏调试信息。
- 顶部信息像状态栏，不像一张冒险地图的章节 HUD。
- 点击可进入节点的 affordance 弱，玩家需要读提示而不是一眼看懂。

### 2. 战斗场上高亮/范围/意图没有统一语言

当前 `isometric_board.gd` 中高亮来源混在 `highlights` 字典里，分别处理 `reachable`、`attack_range`、`targets`、`danger`、`effect_preview`、`paths`。问题是：

- 不同类型高亮的颜色语义不够稳定，移动、攻击范围、效果范围容易互相抢视觉。
- 填充透明度偏重时会遮住角色、意图牌、血条、地形物件。
- 范围、目标、路径、危险区、意图路线缺少统一渲染顺序。
- 敌方意图现在主要是 badge，缺少“将从哪里走到哪里、打哪里”的路线表达。
- 行动选择缺少清晰路径箭头，移动时只看到范围，不够像战棋游戏的确认反馈。

### 3. 下方行动区像网页按钮排，而不是游戏操作盘

当前下方 UI 是一排矩形按钮，虽然功能明确，但缺少游戏操作区的结构感：

- 移动、攻击、宝石操作、结束回合没有形成明确分区。
- 按钮状态更多靠文字和颜色，不够靠形状、图标、位置和节奏表达。
- 信息提示栏像网页 alert/表单提示，和战斗场景脱节。
- “你的回合/第几回合/行动次数/当前模式”混在长句里，阅读负担重。

### 4. 玩家文案有调试腔和 AI 说明书腔

一些文案像是在解释系统实现，而不是游戏给玩家的反馈。例如：

- “点击高亮相邻格前进”
- “地块预览”
- “坐标：(x, y)”
- “事件：event_debug_cache”
- “移动：点击白色边框格（悬浮为路线，每回合 1 次）”

这些信息在调试模式有价值，但不应该作为默认玩家体验。默认文案要短、具体、带游戏语境，只告诉玩家此刻需要知道的事。

### 1. 地图选关卡 UI：从棋盘页改成路线地图

目标感觉：玩家打开地图时，一眼看到“我在哪、能去哪、这条路线有什么风险/奖励、这一章推进到哪里”。

设计方向：

- 用房间节点替代普通地块视觉，把地图当成路线图渲染。
- 节点之间画连接线，表现可行路线、已走路线、锁定路线。
- 当前节点使用强标记：底座、脉冲、旗标或角色小像。
- 可进入节点使用明确 hover/active 状态，不需要靠提示文字解释。
- 已结算节点降饱和并加完成标记。
- 房间类型用稳定图标和少量颜色区分：战斗、精英、商店、事件、休息、Boss/出口。
- 预览面板改成房间卡片：房间名、风险/奖励、可能收益、当前状态。
- 坐标、room_id、event_id、seed 默认隐藏，只在 debug 模式展示。

建议 UI 结构：

```text
顶部：章节标题 / 当前资源 / 路线进度
中部：路线地图主体
右侧或底部：当前 hover 房间卡片
底部小条：返回、查看牌组/遗物、设置等系统入口
```

### 2. 场上高亮与意图：统一 Overlay Spec

新增统一 overlay 描述，不再让各模块直接往 `highlights` 塞散字段。

建议数据模型：

```gdscript
{
  "kind": "move_range" | "move_path" | "attack_range" | "target" | "danger" | "effect_area" | "intent_path" | "selection" | "invalid",
  "cells": Array[Vector2i],
  "path": Array[Vector2i],
  "source_uid": String,
  "target_uid": String,
  "priority": int,
  "style": String,
  "label": String,
  "blocking": bool,
}
```

渲染入口建议：

```text
BattleScene/BattleHudPresenter
  -> BattleOverlayPresenter 生成 overlay specs
  -> IsometricBoard / BoardOverlayRenderer 统一绘制
```

必须统一的 overlay 类型：

- `move_range`：可移动格。低透明冷色填充，弱边线。
- `move_path`：当前悬浮/确认路线。绘制实际路径线和终点箭头。
- `attack_range`：攻击可达范围。只画边线或轻填充，不和危险区混色。
- `target`：可选目标。使用高亮轮廓、角标或锁定标识。
- `danger`：敌方威胁区。红色斜纹/警戒边，不使用大面积实心遮罩。
- `effect_area`：技能/爆炸/毒雾等效果范围。按元素或效果类型区分纹理。
- `intent_path`：敌方下一步路线。使用虚线或短箭头，避免和玩家当前操作混淆。
- `selection`：当前选中单位/地块。最高优先级轮廓。
- `invalid`：不可选/受阻格。短闪红边，不常驻大片遮罩。

行动路径箭头要求：

- 移动或冲刺选择时展示从起点到终点的实际路径。
- 路径必须来自实际寻路结果，而不是起终点直连。
- 终点箭头朝向由路径最后一段决定，即上一格指向终点。
- 如果路径只有一个格，箭头由起点指向终点。
- 箭头绘制在地面 overlay 之上、单位脚底/血条之下，不能遮住角色主体。

建议遮挡顺序：

```text
0 terrain/base tile
1 persistent tile effects: fire, poison, water
2 low-priority fills: move_range, attack_range
3 effect_area / danger pattern
4 path line and arrows
5 props and units
6 unit rings, selection outline, intent badge
7 hp bars, status icons, slot icons
8 hover tooltip / popup
```

颜色方向：

- 移动：蓝青系，低透明，强调“安全可达”。
- 路径：纯色半透明路线线与终点箭头，贴在地块层，不使用厚重描边或白芯。
- 目标：暖白/金色，突出可选目标，不等同危险。
- 攻击范围：琥珀/橙边，少填充。
- 危险：红色，但减少整块透明红，优先用边线、斜纹、角标。
- 毒/火/冰/电等元素效果使用各自元素色，但透明度低于单位 UI。
- 避免高亮同时使用大面积黄绿红，截图里会互相污染并遮挡角色。

### 3. 下方操作区：重做为 Command Dock

目标感觉：底部是战斗操作盘，而不是网页导航栏。

建议结构：

```text
左侧：当前行动单位状态
  - 头像/小像
  - HP/护盾/关键状态
  - 本回合行动点：移动 / 行动 / 宝石操作

中间：主命令区
  - 移动
  - 攻击
  - 拔出/嵌入
  - 取消/返回

右侧：回合推进与持有物
  - 手持宝石
  - 结束回合
  - 当前目标/确认状态
```

设计要求：

- 按钮要有游戏按钮质感：硬边、厚边、按下位移、图标+短标签、热键角标。
- 不要只靠长文字表达状态；使用禁用遮罩、消耗标记、冷却/次数角标。
- 命令分区之间用面板切割、金属/石板边框、内阴影或底座区分。
- 当前选中的命令需要有明确持有态，不只是边框变亮。
- 结束回合应独立放在右侧或右下角，不能和普通动作混成同一排。
- 信息提示条改成短 toast/status strip：只显示当前操作目的或结果。
- 长说明移入 tooltip、检视面板或教程，不占常驻底栏。

建议文案层级：

- 常驻短标签：`移动`、`攻击`、`拔取`、`嵌入`、`结束`
- 状态短语：`选择目的地`、`选择目标`、`选择槽位`、`行动已用`
- 结果反馈：`宝石已拔取`、`槽位已锁定`、`距离不足`
- 详细解释：只在 tooltip/教程显示

### 4. 玩家文案：从系统说明改成游戏反馈

文案原则：

- 默认玩家文案不展示坐标、内部 id、seed、room_id、event_id、脚本名。
- 不写“点击高亮格子”这类 UI 操作说明作为常驻文本；只在首次教程或 tooltip 中出现。
- 不解释实现细节，如“每回合 1 次”“悬浮为路线”可改成状态化表达：`移动未用`、`预览路线`。
- 一条 UI 文案只承担一个任务：状态、指令、结果、警告不要混成一句。
- 用游戏内词汇，不用工程词汇：`房间` 优先于 `节点`，`路线` 优先于 `path`，`威胁` 优先于 `danger`。
- 错误提示要说结果和原因，不要暴露校验流程。
- Debug 文案必须挂在 debug/editor 模式开关后，不进入普通玩家 UI。

示例替换：

| 当前/问题文本 | 建议方向 |
| --- | --- |
| 地块预览 | 房间情报 / 路线情报 |
| 坐标：(5, 5) | 默认隐藏；debug 模式显示 |
| 事件：event_debug_cache | 神秘事件 / 遭遇事件；debug 模式显示 id |
| 点击高亮相邻格前进 | 选择下一间房 |
| 当前：战斗  | 当前房间：战斗 |
| 移动：点击白色边框格（悬浮为路线，每回合 1 次） | 选择移动目的地 |
| 不可进入（需从相邻格走过来） | 路线未连通 |
| 本回合已行动 | 行动已用 |

## Acceptance Criteria

- 玩家不读教程也能分辨：哪里可移动、哪里可攻击、敌人下一步要做什么。
- 地图页看起来像路线选择界面，而不是调试棋盘。
- 底部操作区有明确游戏操作盘结构，不再像网站按钮条。
- 常驻文本短、准、像游戏；调试信息默认不可见。
- 高亮不遮挡单位、血条、槽位、意图 badge。
- 移动/冲刺选择时有实际路线和终点方向箭头。
- 新增 UI 文案遵守 `AGENTS.md` 的文案规则。
